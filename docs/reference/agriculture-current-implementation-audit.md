## 实际机制

### 灌溉和作物

- 地图 11×11，水池在 (0,0)，高度随 y 增大而降低。渠道默认容量 2，升级每次加 2。
- 从水池查找不向更高处流动的可达渠道。最低高度、同高度最小 x 的可达格作为主干目标；非主干候选格按规则形成多个支流路径。这些路径可以重叠，不能把每个支流编号理解成一条互不重叠的物理水渠。
- 每 tick 水池以基准 200 加随机 ±30% 变化；三级蓄水池补缺存余。此处随机浮动不是从主游戏天气系统传入的天气事件。
- 主干先分水，支流随后分水，受容量、上游水量和剩余预算限制。窃流是随后对牺牲支路与受益支路进行的额外调配。
- 作物从四邻水源中选一个：沿渠道到水池距离最小，再按 x、高度排序。水分和海藻精均取该来源；不是四邻供给求和。
- 作物吸水不从渠格扣除相应水量，多作物共享同一渠格的环境数值。埋瓮则从八邻对符合肥料请求条件的生长作物供肥。
- 水、肥、微量累计到作物实例；水肥不足通常在收成结算时判定，微量敏感和藻害可以在生长中扣健康致死。
- 成熟结算后停止吸收和生长，等待收获；产量结合水、肥、微量、土壤、轮作评分以及基础随机产量。

### 超融合与土壤

- 存在超融合且电量大于零时，全图客土吸收率、土壤特殊效果、海藻精 A 面一起启用。
- 无电时客土记录保留，但吸收回到默认盐碱土：水 0.48、肥 0.40、微量 0.38。
- 八种土壤已有吸收差异、轮作、连作、缓释、微量敏感修正等效果；不是尚待设计的空接口。
- 初始储电 500；存在供电超融合时全图每 tick 扣 1，多台不叠加扣电。最后一单位电支持当前 tick，随后关闭效果。
- 断电/补电会调整相关作物周期。诊断中草甸玉米周期 85 → 断电 80 → 补电 85。
- `advanceMapTicks` 只跑模拟核心，不扣电；主游戏用 `runAgricultureMapTick`。因此仅用前者跑通的测试不能证明完整电力行为。

### 海藻精：请求与投放是两个不同环节

- A 面要求有有效作物请求；B 面不要求请求。作物是否请求由定义字段决定，不按当前营养缺口动态判断。
- 当前新作物中有 31 种请求海藻精。登记还要求邻接有水渠道、能够取得灌溉来源。
- 主流请求表收集请求作物，支流表按作物当前受水归属登记。已有有效顺序保留，新增请求追加；没有距离排序。
- 成熟但未收获的作物仍被视作有效请求者；“吸够了”也不会撤销请求。
- 设备主干归属可处理主流和支流；支流归属只处理对应支流。设备归属按邻接流标签优先级决定。
- 选请求时调用注入口可达判断；其中允许“可达请求作物 **或** 可达水流终点”。函数名里的 reachable 不应被理解为严格保证实际请求作物得到海藻精。
- 投放范围为注入口之后至该流终点的有水渠格，不含注入口，也不以请求作物为终点。
- 每个流分别拿设备设定量除以覆盖格数。来源键包含设备坐标和流编号，所以同一设备多个流可以在重叠渠格累加；不同设备也累加。
- 每 tick 清空浓度重新计算，无逐格传播耗时和残留过程。
- 一瓶效果 5000 tick；没有请求也倒计时，再注入重置到 5000，非剩余时长累加。
- 因此已有的是持续请求和自动重新计算，尚不是一个独立持久化的“设备绑定某株作物”对象。

上述请求选择、投放覆盖、多流累加、作物水源选择的核心函数与 Git HEAD 相同；不是本轮作物数据重做新引入的网络规则。

### 投入品、时间与主游戏

- 沤肥默认 1008 tick 一批，正常产出 2～4 份；放气互动全失败时产量还会减少。好氧堆肥产出基质，不能把早期文档的“肥料缩时”当作现行农业作用。
- 三档埋瓮肥的原始供给量为 0.35 / 0.50 / 0.75，随后乘土壤吸收率并取一位小数。
- 一个埋瓮只要本 tick 实际供肥，就耗一单位库存；可以同时供给多个八邻作物。无合格作物时不耗普通肥料。
- 种子、客土和普通注入物走农业物品接口，可使用随身容器和藏身处仓库。面板电池投放走另一套随身容器路径。
- 农业解锁后随全局生存 tick 推进；关面板不会冻结作物。工程仅在面板打开时推进，默认 10 tick、每 tick 5 体力。
- 播种扣种子；收获按实际入包数量增加熟练度，背包只能容纳部分时保留剩余产量。
- 地图状态整体进入存档；工程付款/退款信息 `agricultureTaskMeta` 留在 scene 闭包中，并未随地图 task 一起保存。重启后的工程取消退款是待补充完整集成验证的风险点。

## 已运行诊断结果

执行：`node tools/audit-agriculture-runtime.mjs`。完整输出见同目录 `agriculture-runtime-audit-results.json`。

| 场景 | 实际观察 |
| --- | --- |
| 先种远处请求者，再种近处请求者 | 选择 (6,1)，不是后来种在 (3,1) 的近处作物 |
| 远处作物已成熟且微量累计很高 | 仍选择远处作物；移除后改选近处作物 |
| 一个设备设定 10，处理四个流 | 全图渠格浓度数值之和约 39.9；不是设备全局预算 10。该统计是浓度数值之和，不是物理质量 |
| 同布局再增加设备 | 浓度数值之和约 79.9，确认叠加 |
| 没有请求者时切换 A/B | A 不投放，B 投放；倒计时仍会减少 |
| 芡实有效吸收少量微量元素 | 吸收步骤健康 100→99，专用敏感步骤再到 98，确认重复扣血 |
| 埋瓮放两份高档肥 | 两 tick 后耗尽；盐碱土作物累计肥 0.3→0.6 |
| 地图 JSON 克隆后继续同一 tick | 固定随机条件下与原图一致；不等于完整浏览器存读档验证 |
| 执行主游戏零产量收获动作 | 返回成功，但 crop 仍在 |
| 三份产量只放下两份，再收一次 | 第一次保留一份，第二次清除作物，正常 |
| 执行实际操作菜单函数，水稻地块 | 未建田埂时有播种按钮（播种会被模型拒绝）；建田埂后播种按钮消失 |

## 对既有测试的判断

本次运行全部通过：

- `node tools/verify-agriculture-acceptance.mjs`：13 项，其中包括地图、存档、模拟链路测试。
- `node tools/smoke-agri-power.mjs`。

通过不代表不存在上述问题：验收脚本有多项仅查文本存在；模拟链路绕过操作菜单；地图收获测试直接调用 commit；既有电力周期示例没有草甸土；作物平衡测试预装大量肥料和电力。

新数值已经验证“存在可种配置”和指定布局下的融合收益，但没有验证整个游戏经济中投入品可持续获取、建设空间的总体最优解或玩家实际操作成本。

## 后续讨论可用的边界

- 已有：持续请求、间接布局控制、A/B 切换、融合客土、支流供给、肥料与微量分离。不能把这些重复列成待新建功能。
- 用户提出、尚未实施：按靠近水源选择请求者。距离口径及它对现有投放范围的意义仍需讨论。
- 先区分代码缺口与玩法取舍：零产量收获、支撑建筑播种入口、重复敏感伤害是已复现的实现问题；成熟作物继续请求、多流各取设定量则应先确认设计意图。
- `docs/design/28-seaweed-supply-network-plan.md` 保持未确认草案地位。尤其“供给到请求作物为止”和设备共享总预算都属于改变现行规则，不能当成自然补全。
- 当前证据足以基于实现讨论改进，不足以宣称所有边界均无缺陷或已完成上线验收。

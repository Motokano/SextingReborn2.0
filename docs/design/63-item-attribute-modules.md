## 2. 主表的职责

建议主表只保存：`item_id`、编辑用名称 `editor_name`、分类 `category/sub_category`、通用标签 `tags`、自重 `weight_kg`、可选材质 `material`、属性模块配置引用 `attribute_modules`、可选显示布局引用 `presentation_id`。

- `editor_name` 供策划查找，禁止作为未认识物品的玩家名称兜底。
- 玩家名称和描述由基础大类中的 `identity_text` 分组提供；保留语言认识及各档描述，不直接把 `name/name_0/sn` 机械合成一个公开名称。编辑器默认提供基础入口，不要求每件物品反复勾选。
- 重量是物品自身的质量。组合总重为自重加实际部件，背包负重折减属于携带规则，不改物理重量。
- 目录分类、标签和属性大类分开：苹果可以同时加载食物和材料与生产，目录类别不限制组合。具体能力由大类内实际配置的分组决定；迁移保留既有标签语义。
- `attribute_modules` 是稳定模块ID到该物品模块配置的引用。每种模块最多一份，重复字段不能靠加载顺序覆盖。配置可以复用；实例状态绝不在物品之间共享。
- 大类缺失表示没有该类能力；加载大类不代表启用全部用途。类内可选分组缺失表示不支持该用途，存在但配置非法应报错；不能靠默认0悄悄启用或吞掉错误。
- 物品实例核心另存模板引用、数量、未来实例身份；它们不放入玩家可查询的属性字段集合。

这里的“属性模块”、界面“信息模块”、防具“实物改造件”是三件不同的事。新字段不使用现有实例 `modules` 命名，避免覆盖已安装改造件。

## 3. 大类优先的配置入口

主表只加载以下大类，小用途不再成为独立加载项。字段组是同一份大类配置内的可选结构，不各自建立注册、版本和配置引用体系。

| 大类 | 包含内容 |
|---|---|
| base 基础 | 名称与认知描述、重量、堆叠、交易与货币、腐败、来源和显示引用 |
| food 食物 | 食用、消化、配餐、装盒规格 |
| production 材料与生产 | 烹饪和制药原料、燃料、供水、堆肥、施肥、改土、种子 |
| medicine 药品与使用 | 使用方式、次数、复方成分、成品药效；非药物也可复用使用分组 |
| equipment 装备 | 穿戴、攻击、防护、动作修正、附魔、改造件效果 |
| structure 收纳与装配 | 容量、装配位置、兼容和占用；收纳与连接分别存储 |
| energy 能源 | 容量、初始及剩余电量；普通燃料值仍归生产用途，不重复定义 |
| organism 活体 | 物种、性别、个体特征和畜牧交接状态 |

基础是通用入口，不意味着所有物品都带空状态。货币只填写其中的流通分组；不腐败的物品不初始化腐败计时。重量、身份等主表已有数据由基础接口读取，不再存第二份。数量、归属、地面时间仍由共用物品系统维护。

木材通常只需基础＋材料与生产；苹果是基础＋食物＋材料与生产；电池是基础＋能源；防具是基础＋装备，有可安装部件时再加收纳与装配。生产类只填实际用途，不因加载它就同时获得烹饪、制药和燃料能力。

新增玩法优先扩展既有大类：钓竿性能先考虑装备内的钓具分组，连接复用收纳与装配。只有现有大类无法合理容纳、又具有独立规则与复用需求时才新增大类。不能为了压低数量把一切塞进基础。

信息系统按“大类→有效字段组→已知字段”组织，可按界面合并呈现。没有可见内容就不显示空标题；组内认知条件独立，认识燃料用途不会自动认识制药用途。

主表/实例核心、显示编排、来源、地面时间纳入基础大类的审计视图，实际归属仍遵循共用系统边界。旧轨兼容和保留设计单列不可加载的迁移审计区。未来钓具、磨损优先作为大类内可选分组，不自动新增专属模块。

### 模块粒度与共同字段

- 食用和主动用药分别处理，不强行共用一个无所不包的“使用效果”模块；共有的交互动作可以复用执行入口。
- 食用不自动意味着可作烹饪原料，供水不自动意味着可饮用，可堆肥不自动意味着可施肥。
- `skill_coef` 当前由兵器、手脚装备共用，归攻击载体，不为每类物品复制一份。
- `slots_taken` 是占饭盒格数（43、46号设计及食物目录生成器一致），不能当普通背包占格，也不是进食消化槽。它虽嵌在现有食物目录中，建议归食物装盒模块；46号饭盒实例方案不因此算已实现。
- `segments.*.effects` 是部件按身体位置生效的效果，不是储存在部件中的其他真实物品。
- `food_profile.name` 等嵌套元数据随整个目录载荷审计；迁移时通过字段适配器处理，不把嵌套同名字段误识别为主表字段。

## 4. 模块定义和配置的关系

目标仍分成三类策划职责：

1. 主表：物品ID → 基础信息及加载的属性大类。
2. 模块定义：模块ID → 字段规范、版本、依赖/冲突、状态初始化规则及信息字段定义。
3. 模块配置：大类 → 类内可选字段组 → 具体数值。

第一阶段生成的 `item-catalog-v2.json`、`equipment-catalog-v2.json` 和 `attachment-catalog-v2.json` 将每件物品的模块配置内联在 `attribute_modules` 下，避免迁移期再维护一套可独立修改的配置引用；`item-attribute-module-definitions.json` 单独保存大类、字段组和字段归属。后续出现大量完全相同配置时，可以在不改变运行时读数接口的前提下增加共享配置引用。

模块化目录中的实际结构示意：

```json
{
  "item_id": "example_battery",
  "editor_name": "示例电池（仅编辑器名称）",
  "weight_kg": 0.2,
  "attribute_modules": {
    "base": {
      "identity": { "name": "示例电池" },
      "stacking": { "stack_limit": 1 }
    },
    "energy": {
      "storage": {
        "battery_capacity": 100,
        "battery_charge": 100
      }
    }
  }
}
```

供电定义拥有 `capacity`（模板非负整数）、`initial_charge`（模板初始化配置）、`charge`（实例非负整数）；约束 `0 ≤ charge ≤ capacity`。示例模块配置可以是 `{ "capacity": 100, "initial_charge": 100 }`。新建实例初始化一次，读档、搬运、打开面板不重新初始化。旧模板 `battery_charge` 迁移到初始化配置，旧实例同名字段迁移到剩余电量；缺失的旧状态按原系统迁移规则处理。

每个字段定义必须明确：类型、单位、配置/状态/派生角色、合法范围、缺省策略、引用目标、稳定信息字段ID、显示策略。CSV中观察到string不代表新schema接受任意字符串；例如碳氮字段由消费者按整数使用，迁移时应验证后转型。未知枚举、坏JSON、未知引用、重复定义应在构建阶段失败，并指出物品/模块/字段。

字段重命名只发生在适配层，逐字段清单暂保留旧名便于对账。新模块不允许声明任意全局根字段。新增纯数据变体只新增配置；真正新增玩法仍需实现读取该模块的系统。

## 5. 与信息显示系统统一

### 当前存在的两条路径

- `item-field-display-rules.json` + `ItemFieldDisplayRules`：按字段规则取值，实例优先、模板兜底；支持点分路径、技能条件和renderer。`hidden`、语言类renderer有专门跳过逻辑，所以“表里有规则”不等于已显示。
- `item-info-modules.json` + `ItemInfoModules`：由 `info_module_set_id` 选说明集合，按信息模块判断技能；`tpl_kv/csv_field_text` 主要直接读模板顶层值。此外还有静态说明，不应因没有字段引用就丢弃。
- 标题、重量和具体面板还有既有显示入口，不能仅迁移上面两张配置就宣称信息系统完成。

### 建议的唯一显示链

属性模块提供字段描述 → 按物品加载的模块收集候选信息 → 从模板/实例/派生接口取值 → 角色认知过滤 → 信息布局分组排序 → tooltip、详情、仓库、装备、交易等共用结果。

模块提供信息字段，不直接拼HTML。每个字段拥有稳定信息ID（例如 `power.charge`）、标签、格式/单位、主显示区、顺序、认知条件和未知时处理。布局只引用信息ID，不能自定义第二份数值或绕过认知。能力模块与界面区块允许多对多；按信息ID去重，标题重量等也有唯一主展示位置。

认知过滤返回 `hidden / unknown / estimated / known` 等明确状态（命名为提案），格式化器不得再拿原始隐藏值。不认识某个能力时，连标题、锁定占位、总数、排序、筛选及自动推荐都不得泄露它。已知道这个属性存在但暂不能判断时，才允许符合现有规则的提示。技能级别是一种条件，不替代观察和有来源的检查记录。

迁移默认沿用逐字段清单里记录的技能/等级/renderer和说明模块条件，不能把所有旧字段改成公开。现有电量规则是无技能门槛，是否引入检查条件属于单独的设计调整；本次方案不冒称旧系统已经执行检查认知。`life_planting` 等规则引用还需核对当前技能注册和知识接口，不能沿用历史文档的“已/未登记”结论。

模板初始化配置与实例当前状态必须分开取值。比如已消耗电池的信息模块不能因只读模板而显示满电。取派生属性不得抽样、推进时间、扣资源、写知识或改变实例。

静态风味文案放描述/显示层并保留解锁条件。食物组成文字、经验文字、特殊效果文字由真实模块数据按语言生成，不成为独立玩法字段。

## 6. 重复与历史字段处理

| 现状 | 处理原则 |
|---|---|
| CSV id/weight 与运行时 item_id/weight_kg | 统一导入映射；旧ID引用保持稳定 |
| sn/name/name_0 及多档描述 | 按来源核对：普通物品有构建别名，装备有实际认识档差异；不能全局粗暴去重 |
| food_profile + 顶层饱食/消化字段 | 食物目录覆盖的物品以内嵌目录为现有真源，减少重复展开；目录外逐件核对，不能直接删除顶层值 |
| food_*_text、meal_composition | 作为展示/计算派生；注意meal_composition是组成主类计算结果 |
| battery_charge 同时出现在模板与实例 | 初始化配置和实例状态分离；消耗后的量不能回退成初始量 |
| edible/usable/投料布尔 | 新结构用模块存在表示能力；旧值false时不加载，不能因CSV有列就启用 |
| 所有物品默认有0燃料/0供水/0腐败 | 迁移时依据有效配置和实际用途决定模块存在，不给每件物品装三个空模块 |
| quality | 品质系统已有移除决定；隔离遗留列，消费者/构建兼容确认后删除，不恢复品质玩法 |
| use_effect 与恢复量旧列 | 带废弃标记但当前数据仍出现；逐物品核对有效消费者后转换，不能直接清空 |
| components | 保留配药成分类型/数量含义；不改成真实部件实例集合 |

## 7. k278 实例、装配与持久化的衔接

属性模块负责描述能力与自身变化，物品系统统一负责身份、唯一归属、数量、转移、事务和存档。模块可提供堆叠兼容、初始化、校验、迁移、派生读数接口，但不能自行实现另一套背包或绕过原子转移。

- 复制和保存保留已注册模块状态；未知版本/模块不能悄悄丢弃，进入可恢复的兼容保存或明确拒绝加载路径，具体策略在迁移实现时统一。
- 堆叠必须所有已加载模块同意，真实装配部件的稳定身份不得因同型号合并丢失；数量栈、独立部件、拆堆与合堆的身份政策已在[64号设计](64-item-instance-identity-and-transfer.md)落地。
- 模块的配置版本与实例schema版本分别记录。旧档迁移一次性、可重复检查、避免重复生成ID和重置状态。
- 装配宿主记录真实连接，库存记录收纳位置；禁止循环和重复归属，拆装失败不扣物、不留下半装配。
- 磨损在未来磨损模块持久化；张力/缠绕等归钓鱼作业。跨作业恢复负担需明确时间与归属，不能拆装清零。
- 身份和连接采用嵌套真实实体，组合根占格、后代不重复占格；已在[64号](64-item-instance-identity-and-transfer.md)和[65号](65-item-assembly-and-combined-weight.md)落地。线件断裂仍由62号钓鱼作业结算决定。

## 8. 分阶段实施与验收

1. **字段分类（已完成）**：完成所列源表/显示配置的全量枚举和明确归属；保留旧规则，记录不确定项。产物为本文和逐字段附表。
2. **定义与构建（第一阶段已完成）**：构建器同时生成普通物品、装备、实物改造件三张模块化目录和模块定义表；构建时拒绝未分类字段。旧 `items.json` 暂作为工具兼容产物，不能与模块表分别手改。
3. **共用读数与显示（第一阶段已完成）**：游戏优先装载模块化目录；统一读数接口处理模板值、实例值、零值和缺失值，现有字段规则已接入。旧消费者由内存兼容视图承接，后续按玩法逐步移除顶层字段依赖。
4. **状态、装配与显示（已完成通用切片）**：背包/装备/仓库/地面已接入稳定身份、旧档迁移、唯一归属审计、真实部件连接、组合重量和仓库原子回滚；悬浮说明与背包详情已共用正式连接视图，并支持原子装卸。继续审计贸易/制作/消耗入口和其他信息入口，再由具体玩法读取组合。
5. **全量切换与清理**：现有546+27+16项全部明确声明/引用模块；差异报告解释每个数值变化。删除已无消费者的旧字段/旧显示适配，不永久维护可分别修改的新旧两套属性。

必要验收场景：受损部件装配→拆换→入库→存读档→再拆开保持身份/状态/重量；容量不足或不兼容时原状不变；不同模块状态不误堆叠；电量为0不显示初始满电；药品成分不被当作部件；食物不重复恢复；旧防具效果/附魔/腐败/活体个体不丢失；无认知时不出现隐藏性能和模块提示；模块读数无副作用。

# 农业供给改进方案 v1（讨论稿）

日期：2026-09-11。本文规则已于同日接入当前工作区；验收状态与实现细节见本文末尾“部署记录”。

## 1. 已确认的方向

- 农业围绕放置、环境相互作用和等待收成展开。
- 固定水源，去掉水池升级、窃流、蓄水、溢流和随机供水波动。
- 保留现有主干/支流寻路与分水机制，不顺带重写灌溉。
- 海藻精响应作物的具体需求强度，以适宜生长区间为依据。
- 成熟作物允许继续充当信号，直到完整收获/移除或失去有效连接；自身不再吸收。
- 瓮肥形成储量、缓慢释放，由玩家安排局部肥力；物品档次、生产周期、占格和保质期共同约束。
- 超融合继续同时激活客土和海藻精 A 面。

更新确认（2026-09-11）：同设备重叠取最大值、总能力不足同比缩放、瓮肥平均分配、断电保留 B 面手动设置、按整瓶装入且装不下不扣料、不同档次不混装，已获用户认可。肥料和海藻精在瓶装及设备内均取消保质期。管理目标约 400 tick；游戏尚未上线，版本设计面向未来兼容。拆除工程完成时设备内剩余养分直接消失，取消工程时保留。首轮参数见 28-agriculture-supply-budget-v2.md。

## 2. 固定水源与现有灌溉

水池基准暂用 200/tick。保留渠道默认容量 2、升级增量 2、不可向更高处流动的可达性、最低处/最左主干目标、原寻路排序、主干优先分水、支流顺序与不足时平均分配、上游容量限制。

作物仍从四邻有效水源选择一个，仍按当前沿渠距水池最短等规则取水，不改为相邻水量求和。作物吸水不消耗渠格水量的现行抽象也保留。

分开命名三个概念：渠道格（实际坐标）、水流路径（主干/支流算法结果，可重叠）、设备供给范围（路径注入口之后的有水渠格并集）。支流编号仅供计算和调试，不作为玩家的主要操作对象。

## 3. 海藻精请求规则

### 3.1 按现有可服务路径选择

保留设备当前主干/支流归属及可服务路径集合，不新增网络分区实体。每条可服务路径选择一个有效请求作物；同株可被不同路径选中，但预算按实际渠格合并。

有效请求须满足：品种允许请求；地块仍有作物（成熟也可）；它实际选择的灌溉水源位于设备这条路径的投放覆盖区；设备到该水源之间有连续、方向允许的通水路径。

不能继续使用“能到水流终点就算能服务请求者”的回退。也不能仅因作物任一邻格接触路径就登记成功，必须核对实际取水来源。

### 3.2 距离与稳定性

按请求作物实际取水格沿有效通水渠道回到水池的路径距离升序。这里取当前实际分水连接，不使用穿越干渠的几何近路。距离相同优先保留现任；无现任按固定坐标顺序决定。

新出现严格更近的请求者会接替；同距离不会反复切换。距离定义在只读查询、实际结算和 UI 中必须共用。

### 3.3 生命周期

萌发生长、成熟未收获均保留信号资格，不按累计营养充足与否撤销。部分收获后仍有作物则仍可发信号。完整收获、移除、健康死亡、失去通水关系时重新选举。

成熟作物不吸收，其信号仍按该品种和地块当前生效土壤计算目标。成熟结果不因此继续改变。

## 4. 海藻精目标强度

建议目标取本季适宜微量累计下限 / 本季有效周期，作为每 tick 的适宜吸收下限。仍使用实际作物实例定义，包括旧季定义和周期缩放，避免再建一套作物需求表。

利用现有微量吸收函数反求渠道供给值，计入土壤保留率、土壤特殊倍率和作物倍率。实现时考虑 0.1 精度，不直接用浮点除法后截断，避免显示达标但实际吸收不足。若不存在可表示的适宜值，应显示无法精确满足，而非伪造达标。

不按历史欠缺追赶补灌，不因累计达标停供。不同作物在同一环境里仍可能吸收不足或过量。

## 5. 海藻精覆盖、重叠与预算

保留注入口本格不投放、注入口之后直到当前路径终点投放的范围；请求者不是投放终点。连续通水路径中途断开时，不能隔着断点给远端供给。

对一个设备：

1. 各有效路径得到请求者及目标渠格供给值 C。
2. 把各路径覆盖映射到实际渠格坐标。
3. 同一设备在同一渠格出现多次，取这些路径目标的最大值，不相加。没有重叠的渠格各取自己的目标。
4. 需要的总输出 R 为所有独立渠格目标之和。
5. 设备上限为 P，剩余养分折算后本 tick 可用量为 S；实际总输出 T=min(R,P,S)。
6. 能力不足时统一按 T/R 缩放所有目标，明确展示缺口；不用隐藏的优先级先饿死某支路。
7. 按实际输出扣物品储量，舍入后的累计实际输出不得超过预算；内部使用固定精度单位或明确余数处理。

这里“养分量”沿用游戏供给数值的抽象，预算按渠格供给之和计算，不额外引入真实流体的浓度×体积模型。由数据系数把它换算到每瓶养分消耗。不得同时混用两套单位。

不同设备在同一渠格仍相加：允许加强供给，也可能造成过量。首版不新增跨设备智能协调；UI 显示各来源贡献。

示例：设备两条路径分别要求 1、2，覆盖 [甲,乙] 与 [乙,丙]。合并得到甲1、乙2、丙2，需要5；若上限4，则实际为0.8、1.6、1.6。不会在乙叠加成3，也不会因路径重复免费多产养分。乙上的低需作物仍可能受压，这属于共享环境的真实代价。

覆盖延长会增加总输出需求。未达上限时，设备多耗物料维持目标；达上限后，实际强度下降。因此保留扩大水网的成本，但不再无条件按路径长度稀释每台设备固定设定量。

## 6. A/B 与设备等级

- B 面：玩家手动设定目标供给强度，沿原可服务路径主动投放，不需要请求。
- A 面：根据请求者自动确定路径目标；没有有效请求的路径不投放。
- 两面共用真实物料储量、设备输出上限和坐标合并规则。
- 断电恢复 B 面时使用单独保留的手动设置，不能把 A 面计算结果静默写成 B 面设置。UI 展示断电后的行为。
- 暂保留现有施肥器等级，之后核定其控制范围和总输出能力；不增加新的设备升级分支。旧“浓度范围”与新“输出预算”不等价，不能直接照抄数字。

## 7. 瓮肥

每瓶差/中/优肥对应不同总养分，瓮保存物料批次及剩余养分。沿用不同肥料 ID 不混装的现有约束。瓮容量为同档两瓶；高档肥不因养分更多而反而少装一瓶。

玩家设定释放量 q，受设备输出上限和可用储量约束。服务对象为八邻中需要液肥的生长作物；成熟植物不吸肥也不参与分配，但仍可作为海藻精信号。

推荐平均分配：N 株各得原始供给 q/N，再经过各自土壤吸收。多瓮贡献相加。没有对象时停放，不扣养分；未被土壤保留的部分作为损失，不退库。土壤自身缓释仍单独保留。

不用作物当前缺口自动分配，不为了避免过量自动停供。这样玩家仍通过少种几株、增加瓮、调整释放量、改善土壤解决高级作物条件。

当前 0.35:0.50:0.75 可参考为档次相对效力，不直接作为最终每瓶养分总量。明确区分每瓶养分、每 tick 释放量、土壤实际吸收三个量。

## 8. 物品与生产（按用户确认修订）

三档沤肥暂保留 0.8kg/不可堆叠，海藻精保留 0.5kg/不可堆叠。两类物品统一取消保质期，瓶装及设备内都不腐败；旧物品实例残留腐败计时不再生效。不增加保鲜批次、临期提示或到期损失。

海藻精从定时效果改为总养分储量，按实际投放消耗。原 5000 tick 不直接当成 5000 养分。肥料档次影响每瓶养分，设备设定控制释放速度。按整瓶注入，容量不足则不扣物品；补入同档物料合并养分，档次不同不能混装。

制肥目前 1008 tick 一批、正常 2~4 瓶，碳氮比决定档次；原料总量不线性放大产量。用真实生产能力和约 400 tick 补料节奏共同校准消耗。海藻精稳定获取途径仍需补齐，来源标记不等于已实现生产配方。

## 9. UI：扩展已有改版

保留已实现四视图、来源跳转、区间条、只读预览，不另做第二套农业 UI。

- 水池删除旧等级、随机天气、蓄水、窃流控件，显示固定供水/已分配/剩余。
- 海藻精展示各服务方向的请求者、成熟信号标识、目标/实际强度、总输出占用、剩余养分、按当前投放速度估计的续航。
- 瓮肥展示档次、储量、释放设置、服务株数和每株原始份额/实际吸收。
- 不把内部支流编号当作主要说明；点击路径高亮实际覆盖格，并解释哪里发生合并和不足。
- 收获信号作物、播种更近请求者、切换供电、改渠、调速、补料都应在现有预览入口呈现变化。
- 预览与实际结算共用供给计算；电力、库存导致的未来事件以条件说明，不用当前一刻速率保证最终产量。

## 10. 每 tick 顺序建议

固定水源分水 → 刷新作物受水来源/请求资格 → 计算所有设备目标与预算 → 一次性提交渠格海藻精/瓮肥供给 → 作物吸收及土壤效果 → 微量敏感与藻害各一次 → 生长与结算 → 扣电。

必须基于同一份 tick 输入计算设备计划，再统一提交，避免地图扫描顺序改变分配。不改“最后一单位电支持本 tick”的现行语义。

## 11. 兼容与实施顺序

存档增加农业供给规则版本。请求者用设备、路径信息和作物坐标辅助缓存，但读档时验证可达性，不信任旧支流编号永久稳定。

游戏尚未上线，本轮不做历史付费/升级补偿体系，也不长期并行维护两套水流系统。已有开发存档由明确的版本迁移函数规范化，转换记录可诊断，载入原文件前先保留备份。

区分存档结构版本、供给规则版本、作物平衡版本；载入时补默认字段并限制非法储量，保留成熟/部分收获等实例状态，重建水网和请求关系。以后数值改动时，物品新瓶养分量不得回写到已装入储量，设备降容量不得静默删除剩余养分。物料、规则、作物版本分别决定迁移方式，不能凭字段缺失猜测后永久保留旧路径。

旧海藻精按“剩余 tick / 原总 tick”折算为一瓶养分的同等比例；旧水池升级工程读档时取消。成熟信号、混种季节、部分收获和反复读档纳入回归验证。

实施建议：

1. 完成本文关键规则讨论；修复已复现的重复敏感扣血、零产量收获清理。
2. 固定水源，回归验证灌溉路径和分水结果。
3. 单一设备海藻精请求/目标/实际渠格合并和能力限制。
4. 瓮肥储量、平均分配、物品养分与注入流转。
5. 多设备、断电、成熟信号、物料耗尽与存档兼容。
6. 接入已有 UI，跑真实生产链和全季混种平衡。

## 12. 验收场景

- 相同渠道布局在固定输入下，主干、支流和分水优先级与原分水算法一致。
- 更近作物接替，同距不抖动；干渠近路不会抢请求；实际取水格不在供给区的作物不被选中。
- 成熟保留信号且不吸收；部分收获保留信号，完整收获退出；接替者改变下游强度。
- 同设备重叠路径按坐标取最大值；两个设备仍相加；精度舍入不能突破输出/库存预算。
- 延长水流终点增加耗料，能力不足时正确缩放；无料、无水、无请求分别有明确状态。
- 同一瓮1/4/8株共享、多瓮叠加、成熟退出、黑土缓释和淋溶均正确。
- 瓶装及设备内养分均不因时间腐败；满载拒绝整瓶装入且不扣物品；按实际输出扣量，补料与存读档连续。
- 默认土高级作物需要真实额外投入；客土激活后，同片农田支持更多作物或更低消耗。
- 使用实际1008tick制肥周期和2~4瓶产出验收，禁止把预装无限肥料的模型测试当作经济验收。
